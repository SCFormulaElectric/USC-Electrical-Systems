# Team board test setup

## Start here

From `2026-27/Test Scripts`:

1. Create/activate the Python environment using the OS instructions below, then run
   `python Infrastructure/install.py`. This installs shared and all board requirements
   together and checks dependency compatibility. Resolve conflicts in requirements;
   do not silently give different boards different versions in the shared environment.
2. Create a suite: `python Infrastructure/new_board.py My_Board_Test`.
3. Document wiring and approved limits; edit `Suites/My_Board_Test/bench.toml`.
4. Run `python Infrastructure/run.py -q`, then
   `python Infrastructure/run.py Suites/My_Board_Test --collect-only -q` and
   `python Infrastructure/preflight.py Suites/My_Board_Test --instrument dmm`.
5. After reviewing the physical setup, select a specific procedure:
   `python Infrastructure/run.py Suites/My_Board_Test/test_identity.py -s --hardware`.
   Identity checks establish a connection, not board acceptance.

`--hardware` enables every selected hardware test. The final hardware counts report
execution only; an offline green run does not validate skipped procedures.


For AI-assisted changes, read [AI_GUIDE.md](AI_GUIDE.md). The AGENTS.md files in
Infrastructure and Suites route compatible coding agents to those instructions.
For tools that do not read AGENTS.md, explicitly include AI_GUIDE.md in the prompt.

Day-to-day work belongs in `Suites/<board>/`. Shared tools and dependencies stay in
`Infrastructure/`. Do not put source code inside `.venv`; each computer recreates that folder.

```text
Test Scripts/
  Infrastructure/
    README.md
    run.py                   # Common test entry point
    discover.py              # Read-only Ethernet discovery
    preflight.py             # Validate config; optional identity-only check
    new_board.py             # Create a board suite on either OS
    AI_GUIDE.md               # AI contribution rules
    DRIVERS.md                # Typed APIs and exact command references
    examples/                 # Copyable voltage/sweep/manual/offline tests
    requirements.txt
    requirements-usb.txt     # Optional USB dependencies
    pytest.ini
    backend/                 # Shared pyvisa-py connections and pytest fixtures
    tests/                   # Offline checks for the shared framework
    board_template/          # Copy this when adding a board
    .venv/                   # Local Python environment; ignored by Git
    .pycache/                # Generated bytecode; ignored by Git
    .pytest_cache/           # Generated pytest cache; ignored by Git
  Suites/
    VIL_RML_Test/
      RML/

      conftest.py
      bench.example.toml
      bench.toml             # Your local configuration; ignored by Git
    Your_Next_Board/
```

The board_template and example board contain __init__.py files for Python imports.
Keep them when copying. Board names with spaces can be selected using quoted paths;
underscores are easier when writing imports.

## Install once per computer

Install Python 3.11+. From `2026-27/Test Scripts`:

Windows 11 PowerShell:

```powershell
py -3 -m venv Infrastructure/.venv
.\Infrastructure\.venv\Scripts\Activate.ps1
python Infrastructure/install.py
```

If activation is restricted, use `.\Infrastructure\.venv\Scripts\python.exe` instead
of `python` in subsequent commands. Do not change execution policies just to activate.

macOS Terminal:

```sh
python3 -m venv Infrastructure/.venv
source Infrastructure/.venv/bin/activate
python Infrastructure/install.py
```

Do not copy or move a virtual environment between paths/computers. Its launchers may
contain absolute paths. Recreate it and reinstall the requirements instead.

Both platforms use `pyvisa.ResourceManager('@py')`. Ethernet is the primary workflow;
requirements include psutil and zeroconf for network discovery. No vendor VISA
backend is selected. Optional USB support is installed with:

```sh
python -m pip install -r Infrastructure/requirements-usb.txt
```

USB may still need platform-specific libusb/device-driver setup. Installing Python
packages does not change Windows device drivers. Details:
https://pyvisa.readthedocs.io/projects/pyvisa-py/en/latest/installation.html .

## Everyday commands

From Test Scripts, with the environment activated:

```sh
# All offline checks; hardware tests are skipped
python Infrastructure/run.py -q

# Select one board or one file
python Infrastructure/run.py Suites/VIL_RML_Test -q
python Infrastructure/run.py Suites/VIL_RML_Test/VIL/test_vil_threshold.py --collect-only -q

# Hardware requires explicit opt-in and a reviewed board setup
python Infrastructure/run.py Suites/VIL_RML_Test/VIL/test_vil_threshold.py -s --hardware

# Query Ethernet instrument identities; never changes outputs
python Infrastructure/discover.py
python Infrastructure/discover.py TCPIP0::192.168.1.50::inst0::INSTR
```

Use Infrastructure/run.py, rather than bare pytest, so the shared configuration, backend and
cache locations are loaded. From inside a board folder you can run:

```sh
python ../../Infrastructure/run.py . -q
```

The runner does not change your working directory. Explicit test paths and --bench
paths are relative to your current directory. Without a test path, it runs the
configured Suites and Infrastructure/tests checks. Template files are excluded from defaults.

Discovery can miss devices when multicast is blocked by a firewall/VPN. Supply the
actual VISA address from the instrument's network settings if necessary. The IP above
is only an example; socket ports must come from the instrument manual.

## Add a board

The same command works on Windows 11 and macOS, from any working directory when
you provide the appropriate path to this script:

```sh
python Infrastructure/new_board.py BSPD_Test
```

This creates Suites/BSPD_Test from the template and creates its local bench.toml.
It never opens an instrument, copies personal template configuration or overwrites
an existing board. Case variants of an existing name are rejected on both systems.
Names may contain letters, digits, spaces, underscores and hyphens, must start with
a letter, and cannot be Windows/framework reserved names. Prefer underscores for
Python imports. Quote names containing spaces:

```sh
python Infrastructure/new_board.py "New Board Test"
```

Edit that board's README and local bench.toml. Add your own test_*.py files,
including subfolders if useful. The dmm and glv_supply fixtures are already shared. There is no central
board registry to edit. Each board can use its own instrument names and limits.

The template's test_identity.py is a read-only connection check, not a board test.
Existing VIL/RML procedures are recovered from their misplaced environment folder;
they retain their board-specific preflight and are not commissioned hardware tests.

Vehicle GLV operating range: **11.0-14.4 V**, nominal **12 V**. The template records
this in limits.glv_min_v / glv_max_v / glv_nominal_v. Each board must check its
component ratings and enforce its approved test limits independently.

## Write tests using local fixtures

A board's conftest.py supplies fixtures only to that board and its subfolders. Tests
on different boards can have the same names. Most test files need only `import pytest`;
fixtures are requested as function arguments, not imported. Example for the template's dmm fixture:

```python
import pytest

@pytest.mark.hardware
def test_identity(dmm):
    assert 'EDU34450A' in dmm.identify()
```

For a new instrument, the shared factory also works directly without editing conftest.py:

```python
import pytest

@pytest.mark.hardware
def test_identity(connect_instrument):
    meter = connect_instrument('dmm')  # Looks up instruments.dmm in your board config
    assert 'EDU34450A' in meter.query('*IDN?')
```

The factory identifies each instrument and closes its connections before the VISA
manager, including on test failures. It does not reset instruments or disable outputs.
For a model without a typed shared driver, give its raw connection a short board-local fixture in conftest.py:

```python
import pytest

@pytest.fixture
def scope(connect_instrument):
    return connect_instrument('scope')
```

| Fixture/helper | Purpose |
|---|---|
| dmm | Typed EDU34450A: identify(), read_voltage_v(); query() remains available |
| glv_supply | Reviewed EDU36311A channel; explicit enable and registered OFF cleanup |
| board_config | Load Suites/<board>/bench.toml; no instrument access |
| visa_rm | Open/close @py manager; requires hardware marker and --hardware |
| connect_instrument(name) | Connect by name in this board's config, with automatic connection cleanup |
| from backend import instrument | Public import for advanced custom connection fixtures |

The instrument settings are address, expected identity substring, timeout_ms
(default 5000), and optional read_termination/write_termination (default newline).
The shared helper sends only *IDN? and never resets an instrument or changes outputs.

`--bench PATH` overrides one selected board's local configuration. Runs selecting
multiple boards with this option are rejected before fixture setup. Without an override, each board resolves its own bench.toml
regardless of the working directory. The recovered VIL/RML board has its original
configuration schema; new boards use the generic template schema.

Keep reusable board functions in its helper/ package. Expose the functions test authors
need from the board's __init__.py using internal relative imports. Tests can then use
one stable import at any nesting depth: `from My_Board_Test import calculate`.
The existing procedures demonstrate this with `from VIL_RML_Test import threshold`.
This form requires a Python-compatible board name; use fixtures to expose helpers in
boards named with spaces. Add __init__.py to nested test packages. Do not add sys.path
edits, wildcard imports or a global helper alias: those can mix helpers from different
boards. Do not import another board's conftest or test modules.

Instrument access belongs in fixtures/test bodies, never at module import or
collection time. Mark every instrument test hardware, even read-only ones. The
visa_rm fixture refuses access from an unmarked test. Tests bypassing these helpers
must still follow the opt-in convention; arbitrary Python cannot be policed by pytest.

The shared glv_supply fixture already registers output-OFF before configuration.
For other source fixtures, register output-OFF cleanup BEFORE the first output-changing command. Use try/finally,
a context manager or request.addfinalizer so setup failures are covered. Closing VISA
does not turn a source off. Each board fixture must implement correct commands,
limits, protection, discharge checks and pass/fail criteria using the actual manuals.
Do not run hardware in parallel or against instruments controlled by another operator.

## Short measurement APIs and worked examples

```python
import pytest

@pytest.mark.hardware
def test_glv_input(dmm, board_config, record_property):
    measured_v = dmm.read_voltage_v()
    limits = board_config['limits']
    record_property('glv_voltage_v', measured_v)
    assert limits['glv_min_v'] <= measured_v <= limits['glv_max_v']
```

No SCPI knowledge is needed for this example. `dmm.query()` remains available to
existing code; new measurements should prefer named, unit-bearing driver methods.
Optional type annotations such as `dmm: EDU34450A` (imported from backend) enable
editor method completion. Full methods/configuration and manual sources: [DRIVERS.md](DRIVERS.md).

Copy the relevant file from Infrastructure/examples into your board folder. Examples
cover voltage measurement, a visible voltage sweep, unpowered manual inspection and
an offline calculation. They are excluded from default discovery until copied.
The sweep needs a reviewed glv_supply config and board-specific settling tolerance.
No driver invents a safe current limit, protection level or acceptance tolerance.

Check the selected configuration before a run:

```sh
python Infrastructure/preflight.py Suites/BSPD_Test --instrument dmm
python Infrastructure/preflight.py Suites/BSPD_Test --instrument dmm --connect
```

Without --connect this is offline validation. With --connect it only queries
identities; it does not energize, configure protection, or certify a wired bench.
The recovered legacy VIL/RML schema keeps its own preflight in its board fixture.

## Shared waveform and operator helpers

General calculations extracted from the VIL/RML suite now live in
Infrastructure/backend/measurements.py and operator.py. New boards can use:

```python
from backend import pulse_timing, current_statistics, monitored_input

periods_s, duty_fractions = pulse_timing(samples, dt=0.001, threshold=3.0,
                                       min_cycles=5, active_below=True)
```

- `reading(value)`: finite numeric conversion with overload rejection.
- `ascii_waveform(reply)`: plain ASCII or definite-length IEEE 488.2 ASCII block.
- `pulse_timing(...)`: complete-cycle periods/duty fractions; configurable polarity
  and minimum cycle count (default 30, preserving VIL/RML behavior).
- `pulse_window(values, times, threshold, below=True)`: first complete pulse start/end.
- `current_statistics(current, lamp, threshold, active_below=True)`: ON/OFF/average
  and sampled-peak amps from aligned current/gating samples. The legacy parameter
  name lamp can represent any gating signal, not just a light.
- `monitored_input(question, check=monitor_callback, timeout_s=300)`: console input
  while the caller's monitoring runs on the main thread. All VISA stays in that
  callback/main thread; the input thread only reads text. Requires an interactive
  terminal (-s under pytest). Timeout or monitor error must abort the procedure.

These helpers never choose a board's thresholds, acceptance criteria or hardware
limits. No signal filtering or interpolation is implied; sampled peaks remain
bandwidth-limited. Monitoring callbacks need bounded I/O and independent physical
protection. Console input cannot be canceled portably; do not resume prompting after
an input timeout. The VIL/RML wrappers/import names are retained for compatibility,
while its voltage thresholds, lamp startup semantics and HV fixture remain local.

## Team changes, results and verification

Commit board test code, README and bench.example.toml. Keep local bench.toml,
Infrastructure/.venv, caches and generated results out of Git. Root ignore rules cover these.
Put board-specific dependencies in Suites/<board>/requirements.txt including
`-r ../../Infrastructure/requirements.txt`. Keep shared dependencies in Infrastructure/requirements.txt.

Board authors choose detailed measurement output. Optional pytest reports:

```sh
python Infrastructure/run.py Suites/BSPD_Test/test_identity.py -s --hardware --junitxml=Suites/BSPD_Test/results/run.xml
```

A passing test only proves its assertions; document manual observations and incomplete
acceptance explicitly. Before opening a PR run `python Infrastructure/run.py -q`. Infrastructure/tests
checks multiple boards, duplicate filenames, configuration isolation, quoted board
paths, nested working directories, opt-in and connection cleanup without instruments.
The recovered VIL/RML helper also contains its offline measurement checks.

GitHub Actions is configured for Windows/macOS and Python 3.11/3.13. CI never passes
--hardware. Real device behavior and protection still require bench commissioning.

## Authoring contracts

Shared instrument/config fixtures are function-scoped. Board fixtures depending on
these must also use the default function scope; session/module-scoped bench fixtures
will raise ScopeMismatch. Each test starts with fresh setup. Do not rely on test order.

The runner checks every board conftest before importing suites. Collection/session
hooks and pytest_plugins belong in Infrastructure, not board conftest files. Only
pytest_runtest_setup, pytest_runtest_makereport and pytest_terminal_summary remain
supported for existing board behavior; keep them restricted to that board's items.
Prefer ordinary fixtures. This static check catches common mistakes, not arbitrary Python.

The identity field matches a substring, case-insensitively. A model name accepts any
unit of that model. To bind a bench to a particular unit, use a stable portion of its
actual *IDN? response including model and serial, for example
`identity = "EDU34450A,ACTUAL_SERIAL"` (replace with the real response).

For a custom source fixture, adapt examples/source_fixture.py only for an actual
EDU36311A. Usually the shared glv_supply fixture already does the job. The recipe
registers OFF before configuration; examples for other models require verified drivers.
Its fake-backed failure checks are in tests/test_authoring.py.

Evidence has separate levels: collection proves imports/discovery; offline fake tests
exercise selected logic/failure paths; identity checks identify instruments; physical
commissioning validates the wired procedure. None substitutes for the next level.
